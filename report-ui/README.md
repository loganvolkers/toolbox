# report-ui

The source of `<toolbox-report>`, the element `toolbox report -o web` and `-o html` serve, with
its stories, fixtures and probes
([D01M87PSM9YQGGW3YQ5X4XCJP63](../docs/decisions/D01M87PSM9YQGGW3YQ5X4XCJP63.md),
[D01M880QMWD7Z7FTGKJT99AHWBX](../docs/decisions/D01M880QMWD7Z7FTGKJT99AHWBX.md)). It is about the
box: how it shows reports. TypeScript, Vite, Storybook, Playwright and axe-core are used as they
ship, at the TypeScript and Vite versions `ui/` pins.

The binary embeds one file, `crates/toolbox-cli/src/toolbox-report.js`. It is the Vite bundle of
`src/`, committed so a Rust build needs no Node. Edit `src/`, never the bundle; CI fails when they
differ or when `tsc` does.

| Path | What it holds |
|---|---|
| `src/index.ts`, `src/element.ts` | The custom element: boot, routing, the view switch |
| `src/types.ts` | `ReportData`: the JSON `toolbox report` writes, as a type every view takes |
| `src/views/*.ts` | One module per view (overview, tracks, catalog, entity, campaigns, scorecards, rule, compare), installed on the element's prototype |
| `src/lib/*.ts` | Shared components and helpers: medals, bars, rings, basis badges, the stylesheet |
| `fixtures/*.json` | Report data from real portals, regenerated by `scripts/fixtures.sh` |
| `stories/` | Page stories per fixture, component stories, and the helpers they share |
| `scripts/build.mjs` | The Vite library build of the bundle, and `--check` |
| `scripts/probe.mjs` | The CI probe over every story |

## The loop

```bash
npm ci
npm run storybook          # live stories on http://localhost:6006
npm run build-storybook    # static build, about 2 s
npm run probe              # every story at 1280 and 390 px, light and dark: about 35 s
npm run typecheck          # tsc, strict: about 0.25 s
npm run build              # tsc, then writes the embedded bundle; npm run check verifies it (0.5 s)
```

`tsconfig.json` is `strict` with `noImplicitAny` off until the remaining callback parameters are
typed; a new module should not need the exception.

A probe fails on a script error, a serious or critical axe-core violation under WCAG 2.0–2.2 A
and AA (which includes `target-size`, 24 px), or a page that scrolls sideways at 390 px.
`--filter <text>` probes the stories whose id contains it, and `--out probe.json` keeps the
results. This is the first gate of the maintainer SDLC's `design-review` stage. Judgement the
probe cannot make goes to a blind design audit
([design-audit skill](../plugins/toolbox-operator/skills/design-audit/SKILL.md)), which captures
from the same stories.

## Fixtures

| Fixture | Portal | Shows |
|---|---|---|
| `t4t.json` | Toolbox for Toolbox (`portal/`) | Many tracks, scorecards, campaigns and a measured comparison |
| `openfga.json` | [examples/openfga-portal](../examples/openfga-portal/README.md) over OpenFGA v1.23.0 | A Go repository scored only by generic packages, and a second comparison |
| `openfga-unmeasured.json` | The same, without its comparison records | A comparison not measured yet |
| `starter.json` | [examples/repo-portal-starter](../examples/repo-portal-starter/README.md) over this repository | A small portal with no tracks, campaigns or comparisons |
| `starter-empty.json` | The starter with no connector run | A portal before its first data |

`scripts/fixtures.sh` builds the binary and renders every portal. It needs the tools
`toolbox doctor` lists for `portal/` and the OpenFGA portal; without them, rules read `unknown`.
Never edit a fixture by hand. A state no portal has is a reason to add a portal or a connector
skip to the script, so the fixture stays real output.
