# YAML formatting (D97)

*Status: decided and checked in CI, 2026-11-20 (D97, D98). Tracked YAML is Yamark 0.6.1's fixed point.
`schema/*.json` stays JSON, and `release.yml` stays dist's bytes.*

**Every tracked `.yaml` and `.yml` file except `.github/workflows/release.yml` is the fixed point of [Yamark](https://github.com/posit-dev/yamark) 0.6.1.** CI runs `yamark format --check`. The config is [`yamark.toml`](../../yamark.toml): `compact = true`, so a collection that fits in 80 columns is flow style and a wider one is a block. Folded prose wraps at 72. Markdown and JSON are not selected.

## Why this formatter

The manifests mixed flow objects (`path: {type: string}`) with the same object written as a block, including the JSON Schema fragments embedded in field declarations. An opinionated formatter has to pick one rule for that, and it has to be cheap enough to run on every push.

| Tool | What it decides | On a 4 MB file (the project's own numbers) | On 500 files |
|---|---|---|---|
| **Yamark 0.6.1** | Flow when the collection fits in the line width (`compact`); block otherwise. YAML 1.2 core schema | 79 ms | 0.133 s |
| yamlfmt (google) | Block style, no equivalent "small object stays flow" rule | 184 ms | 3.6 s |
| dprint-plugin-yaml | Prettier-compatible YAML | 1.0 s | 2.6 s |
| Prettier | Both YAML and JSON | 18.7 s | 41.6 s |

The timings are Yamark's published comparison (secondary; see the research log for a measurement on this repo). yamlfmt is the mature alternative and the slower one, and it does not have a rule aimed at embedded objects. Prettier would also normalise `schema/*.json`, which this decision leaves as JSON: the compiler loads those files as JSON, and Yamark's `to-yaml` would turn them into YAML.

## The rule for an embedded object

A field schema that fits stays on one line:

```yaml
path: {type: string}
```

A schema that does not fit becomes a block map, with the same key order. Both are the same rule, applied at 80 columns. Indentation is 2. A sequence nested under a compact key is indentless (`- item` at the parent's column).

Yamark 0.6.1 is not idempotent on the first pass over those sequences: the first format leaves them indented and the second dedents them. The second pass is the fixed point, and it is what `--check` accepts. Run `yamark format` until `--check` passes.

## Values that must survive

Yamark emits YAML 1.2. A plain `2026-09-02` is a string, `true`/`false` are booleans, and `yes`/`on` are strings. Seikika's parser (serde_norway) agrees. PyYAML 1.1 does not: it reads a plain timestamp as a `datetime`. The reference tools load YAML through [`yamlutil.py`](../../examples/reference-portal/tools/yamlutil.py), which drops that resolver, so `tools/reference.py` and `tools/validate.py` keep the string. Quoted dates are not a style we preserve, because the formatter removes quotes that YAML 1.2 does not need.

Yamark 0.6.1 corrupts an unquoted flow value that contains an apostrophe, turning `{type: string, description: The assessor's summary.}` into `{type: "string, description: The assessor's summary.}"}`. Double-quote that value. The formatter leaves the quoted form alone, and the parsed string is the same.

`schema/*.json` is unchanged. A JSON formatter for those files is a separate decision.

`.github/workflows/release.yml` is generated by `dist`, and `dist plan` rejects the file when its bytes differ from that generator (D98). Yamark's flow style is a different byte string, so the check excludes that one path. Regenerating it is `dist generate`, and the result is committed as dist wrote it.

## Check

```bash
python3 -m pip install yamark==0.6.1
yamark format --check $(git ls-files '*.yaml' '*.yml' ':!.github/workflows/release.yml')
```
