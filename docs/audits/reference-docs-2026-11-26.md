# Reference documentation audit

Give precise lookups a single **Reference** home beside **Guides** in the docs sidebar. Render Seikika's HTTP, command, and MCP references in Starlight. Use docs.rs for published Rustdoc, and npm and editor hovers for the released Vue and Astro packages. This keeps the version and search features that readers already use for those packages.

## Research method

I compared the published guide and reference entry points, how each reference matches source or release artifacts, and what a reader can look up at the destination. I then checked Seikika's router, `seikika describe` records, package exports, schema files, and existing routes for the same properties. The examples cover a shared docs site, a separately rendered HTTP reference, and language-specific reference hosts.

| Source | Observed practice | Application to Seikika |
|---|---|---|
| [Diátaxis reference](https://diataxis.fr/reference/) | Reference follows the structure of the product and supports precise lookups. Guides are organized around what the reader wants to accomplish. | Give Reference one entry point organized by interface. Keep quickstarts and audience workflows in Guides. Cross-link at the point of use. |
| [Google API reference comments](https://developers.google.com/style/api-reference-comments) and [AIP-192](https://google.aip.dev/192) | Describe every public surface, including inputs, output, and failures. Put machine-readable descriptions on the source definitions that tools consume. | Show MCP argument names, required fields, types, choices, and descriptions from the existing `tools/list` definitions. Keep SDK comments in source and shipped declarations. |
| [Kubernetes Reference](https://kubernetes.io/docs/reference/) and [reference generator quickstart](https://kubernetes.io/docs/contribute/generate-ref-docs/quickstart/) | Reference is a sibling of task sections. It indexes the API, CLI, and configuration. Its generation workflow produces different kinds of pages and files from source. | Present several interface types in one navigation group. Use one native docs shell for Seikika-rendered lookups while keeping the source appropriate to each interface. |
| [Stripe documentation](https://docs.stripe.com/) and [API reference](https://docs.stripe.com/api) | The API reference has its own entry point for operations and parameters, links to client libraries, and points back to the development quickstart. | Give REST a clear link from Reference and from the guide. Link language SDKs by package. Keep setup instructions in a guide. |
| [GitHub REST OpenAPI description](https://docs.github.com/en/rest/about-the-rest-api/about-the-openapi-description-for-the-rest-api) and [OpenAPI 3.1](https://spec.openapis.org/oas/v3.1.1.html) | GitHub publishes a machine-readable description alongside the human reference. OpenAPI defines paths, operations, schemas, and security requirements that consumers and generators can use. | Use the existing HTTP reference and source router now. When the per-portal OpenAPI contract ships, generate the operation lookup and typed clients from the same versioned description. |
| [AWS JavaScript developer guide](https://docs.aws.amazon.com/sdk-for-javascript/v3/developer-guide/welcome.html) and [SDK reference](https://docs.aws.amazon.com/AWSJavaScriptSDK/v3/latest/) | A task guide points to a separate versioned SDK reference. | A guide can lead to a reference with a different renderer. Give package names and version guidance before the reader leaves the site. |
| [Rustdoc on docs.rs](https://docs.rs/seikika-connect/0.2.1/seikika_connect/) and [docs.rs build metadata](https://docs.rs/about/metadata) | The published Rust reference is browsable by crate version and item, with Rustdoc search and source links. Cargo metadata sets the build feature and target selection. | Link the existing docs.rs build. Duplicating it on the site would add another build, version selector, search surface, and set of URLs to maintain. |
| [TypeDoc](https://typedoc.org/) and [output settings](https://typedoc.org/documents/Options.Output.html) | TypeDoc can generate TypeScript API HTML or data and supports presentation options. | For two packages, released README tables and declaration hovers already carry the lookup. Evaluate a generator once it can cover the Vue props and slots, Astro options, and CSS tokens that callers use, alongside TypeScript symbols. |
| [MCP tools specification](https://modelcontextprotocol.io/specification/2025-06-18/server/tools) and [Starlight sidebar](https://starlight.astro.build/guides/sidebar/) | MCP servers advertise tool definitions and input schemas through `tools/list`. Starlight supports manual navigation groups and folder-generated groups. | Render built-in tool schemas from the same definitions and point to `tools/list` for portal-specific actions. Use a manual Reference group and keep generated directory links for connectors and packages. |
| [WCAG 2.2 consistent navigation](https://www.w3.org/WAI/WCAG22/Understanding/consistent-navigation) | Repeated navigation appears in a consistent order, which helps readers find it across pages. | Use the sidebar readers already use on desktop and mobile. Retain existing URLs and stable item anchors. |

## Inventory and publishing choice

| Surface | Existing authority | Reference entry |
|---|---|---|
| HTTP catalog and action APIs | Axum router and integration tests. The public page documents common reads, actions, version waits, and errors. | [HTTP API reference](../../site/src/content/docs/users/api.md). Keep its existing route and headings. Per-portal OpenAPI and client generation are on the [user SDK roadmap](../design/user-sdlc.md#5-gaps-to-close-proposed-order). |
| Built-in MCP tools | The server's `builtin_tools()` array. The running portal advertises its own actions. | [MCP tool reference](../../site/src/content/docs/reference/mcp.mdx). Generate tables at build time using `seikika describe`. The CLI and MCP fingerprint detects source changes in CI. |
| CLI commands | `seikika describe` and commands' own `--help`. | [CLI reference](../../site/src/content/docs/start/cli.mdx). Keep its command deep links and link to the MCP lookup. |
| Rust connector SDK | Crate source and published Rustdoc. | [SDK reference](../../site/src/content/docs/reference/sdks.md) links to docs.rs for the installed version. |
| Vue and Astro packages | Published READMEs, comments on shipped types, and Storybook. | SDK reference links to both npm packages, the existing [npm directory](../../site/src/content/docs/authors/npm.mdx), and rendered examples. |
| Portal configuration, protocols, and integration inputs | The four checked-in JSON Schemas, manifest guide, connector field references, and action README. | [Contracts and schemas](../../site/src/content/docs/reference/contracts.md) links to those sources and gives release selection guidance. |

## Navigation and styling

**Docs** names the whole site. **Guides** answers how to finish a task. **Reference** answers what an interface accepts, produces, or exposes. These are sibling choices in the existing sidebar, with a Reference shortcut on the site home. Connectors and Packages retain their directories and generated navigation. Both the site and guides link to the canonical reference routes, including the historical CLI, HTTP, and manifest paths.

Use Starlight's default components, search, and semantic markup for the content hosted here. Keep generated Rustdoc's presentation on docs.rs. A bespoke theme or renderer makes sense when it solves a concrete lookup problem, such as version selection or deep links to operations. Evaluate it against link stability, keyboard and narrow-screen use, and source-to-reference drift before adopting it.

The [writing guide](../../site/src/content/docs/maintainers/writing.md) records the editorial policy. The [navigation decision](../decisions/D01M8DDGT9KEVE4PSJ3WV7C44NE.md) records the publishing boundary.
