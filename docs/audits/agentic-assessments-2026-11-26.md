# Seikika agentic assessment review

Maintainer SDLC, repository-first. This is an audit of the box that selects, validates, stores, and reports assessment evidence. It covers the assessment contract, PR feedback, and the maintainer design-review loop. Repository revision `ab60efa`, 2026-11-26.

**Keep bring-your-own-harness. Give Seikika responsibility for deciding what needs review, what evidence is sufficient, and when another run is worth paying for.** PRs #87, #91, #126, #135, and #139 supply concrete cases for executable checks. PR #108 shows another failure mode. The project previously blocked on unrelated stale reviews, and the opt-in replacement checks staleness without requiring coverage of the affected subjects. Fix that policy boundary before expanding agent-driven gating. [Historical replays](#historical-replays) · [Assessment freshness preflight](../RELEASING.md#assessment-preflight)

Start with a deterministic PR assessment plan, a small set of independent checks, and a bounded advisory delegate pass. Track open findings and review coverage by changed subject. Ratchet deterministic regressions and explicit review obligations. Use a targeted browser task or a human decision to resolve uncertainty about a design. [Judgement as data](../decisions/D01M7WHQA9G0000000000000000.md) · [Design audit](../design/design-audit.md)

## How the current system behaves

| Surface | What works | What needs improvement |
|---|---|---|
| CLI and MCP briefs | A portal defines rubrics for catalog kinds. `assess brief` and `assessment_brief` provide an entity, criteria, facts, subject hash and a submission template. The same brief works with the developer's existing agent or a person. | Each brief starts with one entity. There is no PR base/head plan that chooses relevant criteria, assigns tests, records exclusions, or asks for evidence on uncovered changes. CLI `brief` and `check` derive the portal via `report::live`, so processing a small scope can pay for unrelated connector work. |
| Local and remote results | Assessment YAML and `assess submit` produce records. The workspace connector resolves local citations and can associate a grounded, named second review. The catalog can show a judged scorecard next to a measured one. | `assess check` validates files under `assessments/` and compares subject hashes. `assess submit` checks the local manifest and posts to ingest. These paths apply different citation and grounding checks. A rubric question can change while the entity hash still matches. A single rubric/entity ID represents the latest result, which makes competing attempts, provenance and disagreement hard to audit. |
| Validity and authority | Missing criteria fail validation. Workspace citations and `meta-assessment` enforce useful conventions. Some review scorecards keep stale failing criteria visible and the review-of-review rule stops after one level. | Duplicate contradictory verdicts validate. Citation existence does not establish support for a claim. Different self-reported assessor names do not establish independence. New or replaced results need a consistent policy for duplicates, exact scope, provenance, and superseded findings. |
| CI and the results baseline | Judged `review-*` scorecards are advisory, and `meta-assessment` ratchets record quality. The `require-fresh-assessments` label enables strict staleness checking. The workflow cancels superseded PR jobs. | Strict checks fail on stale rows anywhere in the portal and return success for missing rows or fresh `fail` rows. CI validates form and compares a deterministic baseline. A green check says little about whether an author got an independent judgement on this PR. A `meta-rubric` rule also treats universal passes as a signal to investigate. It should never create demand to manufacture failures or review every entity. |
| Design review | Storybook probes, axe, multiple reference portals and reader tasks were already adopted. Fresh blind judges uncovered task and wording issues that those probes missed. | Three judges at every iteration multiply cost. Panels can start twice, early stop depends on passing rounds, and ordinal variance can reopen a loop. The run records omit usage and attempt admission, so an operator cannot attribute or cap the spend. |

Thirty-one of 220 dimension comparisons fell, and only five rounds had zero declines. A retrospective cap that admitted two extra audits after round 14 would have avoided **20 of 36** auditor starts, assuming identical earlier decisions. ## Proposed design

### Select checks before spending on judgement

1. **Produce a PR assessment plan.** Accept a base/head pair and a portal. Use the immutable diff, manifest and include versions, plus a small checked-in mapping from relevant path or dependency changes to subjects, probes, rubrics, and risk. Use trusted base policy to choose required checks and show candidate policy changes in the diff. List planned and skipped work, why it was selected, and mandatory evidence. Across renames, deletions, generated files, and shared dependencies, either resolve affected subjects or emit `scope_unknown` with an owner for triage. Reuse the CLI and MCP brief builders for each selected subject.
2. **Run known checks first.** Match the defect class to an independent executable. Start with release/onboarding and SDK consumer smoke, acceptance failure diagnostics, and Storybook rendered states. Read normalized results and artifact digests from existing slots, and keep ordinary CI as the executable authority. Highlight new finding identities alongside score deltas. Equal counts can hide a newly introduced defect if an old one was fixed in the same patch. [Ratchet identity gap](../design/ratchets.md) · [Existing tool contract](../design/seikika-and-tools.md)
3. **Delegate the remaining questions.** Hand the host a bounded packet with the diff, applicable rubric criteria, required task outcomes, check evidence, changed paths, and known open findings. Accept `pass`, `fail`, or `unsure` with a criterion, severity, evidence reference, suggested remedy for a finding, and checked/skipped scope. A healthy pass has coverage. A missing or unreadable prerequisite is `incomplete`. An adapter reads and returns data from a read-only snapshot, with trusted runner identity recorded separately from the result's model label. Product writes, repository credentials, and publish credentials stay with the caller's CI or local process.
4. **Validate and decide.** Apply common validation across file, CLI/MCP-assisted and remote ingestion paths for the new result format. Check one outcome per criterion, correct subject kind, pinned source and rubric digests, evidence ranges on the immutable tree, check artifact provenance, and unique attempt or idempotency IDs. Use authenticated submitter and runner identity for independent signed approvals where required. Keep immutable attempts and allow a later result to update the current projection only if it matches the active head and plan. Preserve an open finding until a repair has evidence or an owner dismisses it with a reason. A stale pass loses authority while a stale open finding retains its history. Keep v1 `assess check` semantics compatible and expose stricter coverage through an explicit scoped mode or command.

For normal PRs, the deterministic ratchet decides the merge check and judged results appear as advisory. When policy requires independent review for a named high-risk subject, use a separate obligation with `satisfied`, `needs_owner_decision`, or `incomplete`. A human acknowledgement or a passing required probe can satisfy a policy-defined obligation. Surface budget deferrals and missing evidence on the active head. Keep emergency waivers scoped, attributed and expiring. [GitHub Actions concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency) · [GitHub Check Runs](https://docs.github.com/en/rest/checks/runs)

### Bound the work a review can trigger

| Control | Initial pilot policy |
|---|---|
| Trigger and deduplication | Trigger on ready-for-review, a meaningful scoped change, or a maintainer request. Use one active plan per PR and coalesce superseded heads. Deduplicate delivery by repository, PR, head, plan digest and adapter slot. Reuse evidence across heads only when inputs, tool/rule versions and policy digests match. Merge messages about the same cause into one finding with an identifier that survives line moves. |
| Admission | Start with **two judgement invocations per PR per rolling hour, eight per repository per rolling hour, one active invocation per PR, and three automated starts per review cycle**. A cycle starts when the PR is ready for review and survives further pushes. Each judge and retry consumes a start. Retry a transient failure once if the same plan is current and budget remains. A deliberate maintainer override writes a reason and allocates an explicit new ceiling. Deterministic checks run on every eligible push. |
| Work per invocation | Pilot with a 12k-token evidence-packet target, six model steps or turns when supported, and a five-minute wall deadline. Start with a 32k total-token allowance for metered execution and set a provider-native stop where available. Allow bounded evidence reads or explicit deferral when the packet is insufficient. Cancel the process tree on expiry or superseding head. Meter cached/uncached input and output according to adapter semantics and report any observed overrun. |
| Enforcement boundary | A managed adapter reserves capacity atomically before launch and settles usage after completion, even for aborted attempts. Use a lease and dedup key so retries, collisions, and worker crashes do not open more allocations. Legacy/manual push remains available with reported or unknown usage. A cap shown as hard requires a runtime that enforces it before new model requests, including tool-loop calls. A stream that reports usage after the call supports reconciliation and a soft stop. |
| Design loop | Run state/task probes after each change. Schedule one blind judge at a decision point with a new artifact or unresolved reader task. Admit another only for a high-impact disagreement or a release checkpoint. Close the automatic loop after two admitted rounds without new material evidence, or when its start budget is reached. Escalate unresolved severe findings to their owner with the exact blocked task and artifacts. Track same-fixture disagreement and keep the original score visible instead of using ordinal fluctuations to schedule more work. |
| Telemetry | Record decision reason, adapter and model version, base/head, scope, run state, wall time, tool calls, usage source, input/output/cache tokens where available, estimated cost, and a pointer to evidence. Report starts, cancellations, duplicates, deferrals, coverage and findings resolved per PR and per loop. Keep high-cardinality PR identifiers in run records and traces. Publish aggregate metrics by harness, rule family and outcome. |

Treat the numerical limits as tuning parameters. Start in the repository workflow with its existing concurrency controls and a runner-owned ledger. A served rollout can use Postgres for atomic reservations across workers. Persist enough metadata to resume safely without making a job manager or model account a deployment prerequisite. ## Pilot and decision criteria

1. **Land a deterministic plan and replay checks first.** Add the known states to CI using existing format adapters. Add validation fixtures for duplicate verdicts, stale results after rubric changes, and missing scoped review. Measure current coverage and previous PR misses in shadow mode.
2. **Evaluate delegated review in shadow mode.** Pre-register at least 20 additional historical PRs across docs/release, SDK/API, CLI/acceptance and UI, plus clean controls. For a reviewed defect, use the last head before the fixing change and the merge base, and hide later reviews, fixes and test answer keys. For follow-up repairs, pin the failing and repaired revisions and use human-confirmed tests or PR evidence as gold. Keep tuning cases separate and split related PRs by cause. Play issues the probes could catch and genuinely judgement-heavy cases.
3. **Compare four arms on frozen inputs.** Run current `brief`/push workflow, deterministic probes alone, OCR delegate with the same host/model, and Seikika's bounded probes-plus-delegate plan. Use fresh sessions with pinned adapter, model, effort, tools and fixture versions. Run at least three independent trials per judgement arm, and at least five when registering a cost hypothesis under Seikika's protocol. Balance trials across PRs, use the same wall and usage constraints for direct delegate comparisons, and verify usage collection before scoring cost. Two blinded reviewers independently match findings by root cause and severity, resolve disagreements, and adjudicate new defensible findings using reproducible evidence.
4. **Set a bar before switching on enforced obligations.** Track issue-level known severity-3/4 recall and grounded precision, actionable false positives per clean PR, coverage of required subjects, time to first actionable finding, p50/p95 tokens and latency, and starts per PR/loop. Also report completion rate and the token-metered fraction. Start by requiring every named deterministic control to catch the before case and pass the repaired control. Pre-register a severe-recall non-inferiority margin, target at least 80% actionable precision, and test for at least 30% fewer model starts and, where metered, fewer tokens at matched coverage. Publish denominators, paired differences and PR-clustered uncertainty, plus qualitative losses and budget exhaustion. Run a power check and report an inconclusive comparison when the corpus cannot support the bar. Track assessor agreement per criterion and hold back any obligation whose coverage or adjudication is unstable.

Start with the two rendered state probes and the scoped assessment contract tests. They address regressions with direct evidence and establish the measurements needed to decide whether broader automated reviewing earns its cost.
