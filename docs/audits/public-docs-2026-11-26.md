# Seikika public documentation gap analysis

**November 26, 2026.** The live Seikika docs scored **33.75/100** against **91.25/100** for Backstage's stable public docs. The revised Seikika docs score **81.25/100** against the same rubric. The largest initial gaps were a broken install path, shared deployment and access control, version guidance, and the lack of a symptom-based recovery guide.

The revised site covers both first-use journeys, repository scoring and a running catalog. It also covers changes, deployment, permissions, package and connector authoring, HTTP and MCP reads, and self-service actions. Backstage still sets a higher bar for the depth of operational guidance, detailed reference for larger integrations, and public version policy.

## Scope and method

- Audited the 31 content routes in the public Seikika site, its report and Storybook entry points, the public repository README, and release assets. Used source revision [`c14c9fb`](https://github.com/seikika/seikika/tree/c14c9fbb60405f9fea12d86de3d0b32b717755d9) and the [successful Pages build](https://github.com/seikika/seikika/actions/runs/45785399385) to identify the baseline. All 31 content routes returned HTTP 200. The first install link to the [0.2.0 release](https://github.com/seikika/seikika/releases/tag/v0.2.0) returned 404. The accessible 0.1.1 release listed `toolbox-*` installer assets. [Seikika docs](https://seikika.com/), [release list](https://github.com/seikika/seikika/releases).
- Compared the equivalent reader journeys on Backstage using its stable docs. Used six open-source projects or frameworks as targeted baselines for the jobs their docs explain well. Checked official docs and repositories. Commercial portal pages informed related Seikika copy and were outside the scored sample. The comparison is a structured expert review. Seikika's examples were executed where noted. Peer examples were reviewed in the published pages.
- Counted supported workflows. For example, Backstage's TechDocs and Scaffolder illustrate how to teach publishing and actions. Their presence does not make an equivalent Seikika feature a documentation requirement. Product gaps and pending releases affect what can be demonstrated.
- Scored each category from 0 to 4. **0** means absent. **1** means scattered, stale, or the entry path blocks the task. **2** means partial with a material omission. **3** means the main task is findable and complete within a stated scope. **4** adds strong evidence for edge cases, usable examples, clear version scope, or a clear path to deeper help. The weighted contribution is `weight × score / 4`. Scores are ordinal judgments with published evidence, so the decimals indicate arithmetic precision only.

React's team documented its investment in interactive examples, diagrams, exercises, and a separate curriculum and reference. Its 2023 announcement also describes earlier adoption of Hooks and how the old learning sequence became harder for beginners. That evidence supports a specific practice: remove unnecessary prerequisite knowledge and let readers learn by doing. The sources do not establish how much React's documentation caused overall adoption. [Introducing react.dev](https://react.dev/blog/2023/03/16/introducing-react-dev).

The style guide also draws on Diátaxis for page intent, Google and Backstage for direct and respectful prose, Kubernetes for technical conventions, and W3C for accessible content. The grade ranges in the guide are editorial targets for Seikika's audience. W3C's reading-level criterion is a Level AAA criterion with requirements for supplemental material or a simpler version in certain circumstances. The targets are not a conformance claim. ## Priorities and maintenance

1. **Keep install and first success working on each release.** Check public asset names and the selected starter revision when a release changes. Build and run the source fallback from a clean checkout. A new user should be able to create a baseline and reproduce the documented exit codes.
2. **Keep shared deployment and security examples tested.** Exercise a Postgres deployment, readiness, and allowed and restricted reads whenever auth, persistence, or connector setup changes. Add provider-specific examples once a source or release build can verify them.
3. **Publish explicit contracts as they stabilize.** Generate a portal API description when that feature ships. Add maintained release-versioned references and an upgrade matrix when there are multiple supported Seikika release lines. Extend the coexistence pilot into a field-by-field migration guide when a migration tool or verified mapping warrants it.
4. **Maintain the writing standard in review.** Run examples and check real outputs in the affected role. Inspect live links when moving pages. Revisit the scorecard after a material release, and use recurring support issues to decide which recovery cases to add.

## Verification boundaries

The tutorial, API, MCP, connector, and Git package examples were checked against the pinned 0.2 source on Linux. The source deployment was checked with Postgres 16, OpenFGA 1.22.1, and a personal access token. The federated actions acceptance suite ran in disposable repositories and passed. Release installers, cloud provider deployments, and a full Backstage migration were outside this verification.

All 41 content pages reached gold on Seikika's structural scorecard. The Astro build, rendered route and anchor checks, and browser smoke checks passed. The mobile browser check covered keyboard entry, the quickstart route, and copying a command. These checks complement the editorial review and workflow tests.
