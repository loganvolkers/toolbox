## The review, as reported

*Reviewer: independent, did not design or build the code under review. Code reviewed at
`cursor/federated-actions-f7e8` @ `117c608` (plus `e307c52`, which landed during the review, noted
in F3). Binary: `target/debug/toolbox` copied to `/tmp/review/bin`. Scratch work: `/tmp/review/`
(the org built by `scripts/m5-acceptance.sh` with `KEEP=1 TMPDIR=/tmp/review`, kept as
`/tmp/review/tmp.CvlTiozjRh`). `scripts/m5-acceptance.sh` passes (all seven steps). The
repository was not modified.*

### Verdict

**Not ready to unpause M5 as built.** The lifecycle core is sound: stale-token checks, refusing
self-approval by exact match, `unverified` for actions with no postcondition, and change runs
started from the remote base in a worktree. But the federation trust model is inverted.

- **The parent trusts its children's manifests, the opposite of what T1 and T2 claim.** A child
  portal's `federation.runner` chooses which of the parent's environment variables is sent as a
  bearer token, and to which URL (F1). A child that says `runner: local` gets its code run inside
  the parent server's process, with the server's whole environment, by any caller who asks for a
  *preview* (F2).
- **Approval is not bound to anything durable.** In a checkout it is a pair of self-asserted
  flags (F5). In `serve` it is not bound to the definition that was approved (F6). It races with
  itself and with cancel (F7). It is accepted over MCP and from any token, against D57 (F10).
- **"Done means observed" degrades silently in three places.** A served change run sticks in
  `verifying` and reads the wrong tree (F8). An unmerged pull request reports `succeeded` when
  the base already satisfies the postcondition (F9). A dispatched workflow that never appears
  stays `dispatched` forever (F15).
- **The audit trail is mostly self-reported.** Records are unsigned, in-memory files that
  `--verify` trusts completely. A hand-edited record can even execute code through a `git` option
  (F11).

Most fixes are local: the parent owns its runners, approvals get compare-and-swap and binding to
the action version, records are validated, and the postcondition is bound to the run. They should
land before the review is marked as folded in.

### Design-to-code contradictions (folded into the findings above)

- T1 and T2 against F1 and F2. The MCP text "Has no side effects" against F2.
- §8 "JSON Schema, checked at preview" against F12.
- §6.2 and v1-spec §7.5 say `github-workflow` is "tracked by run id" and uses
  `return_run_details`; the code matches on `run-name` (F15).
- §6.3 says a run succeeds "only when its postcondition held at a snapshot after the run" (F8, F9).
- D57 (human-only approvals, not MCP) against `approve_run` (F10).
- v1-spec §7.5 says executors run "as a separate Unix user with only their declared secrets"; they
  inherit the whole environment (F2).
- action-runs §2 lists `timed_out` and `compensated`; nothing emits either (F15, F19).
- v1-spec §6.6 says approvals are a "durable wait"; they live in memory (F18).
- §7.1 step 7 and S5 say "another maintainer's approval" is tested; it is tested only in dev mode
  (F20).

### What holds up

- **No shell interpolation of inputs.** Inputs reach commands as `TOOLBOX_INPUT_*` and stdin
  JSON, and argv form is supported, so the injection risk is limited to how a command uses its
  variables. F12 is the schema gap, not the executor.
- **Stale previews are refused** when the inputs, effects or the entity's facts change (exit 1 /
  `409 preview-stale`). Invalid inputs exit 2. The 10-minute TTL works for honest tokens.
- **The requester's own approval is refused** by exact principal, in both `serve` and the CLI.
  Rejecting needs an approver. The last approval re-prepares *as the requester*, so permission,
  preconditions and blockers are checked again (but see F6).
- **A run without a postcondition ends `unverified`**, never `succeeded`. A federated run reports
  the child's verification with `{by: child portal}`. The workflow token is never written to a
  record.
- **The change executor is careful with git.** It starts from `origin/<base>` in a detached
  worktree, uses a unique branch per run, never force-pushes, writes `Toolbox-Run` and
  `Requested-By` trailers, and fetches before verifying in the CLI.
- **Permission checks fail closed.** A relation missing from the model is a deny
  (`access.rs:188`), and a served parent refuses children that declare no runner (`409 no-runner`).
- **The acceptance script runs offline** (no network, no Postgres) and passes.
