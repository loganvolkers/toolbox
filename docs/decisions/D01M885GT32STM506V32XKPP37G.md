# Cargo.lock advisories are scored against a pinned RustSec snapshot, and each accepted one is justified in osv-scanner.toml

**Toolbox for Toolbox scores the `Cargo.lock` it ships with osv-scanner, offline, against
RustSec's OSV export at one pinned commit. The scanner goes through the SARIF slot (scorecard
`maintainer-advisories`), so it is ratcheted like any other tool. An advisory with no fix that
applies is ignored in `osv-scanner.toml` with its reason, and with no expiry date.** This is O5
of [openssf-template.md](../design/openssf-template.md). It covers Cargo.lock only. Scorecard's
live Vulnerabilities check stays out of the ratchet.

1. **Why a pinned snapshot.** A ratchet needs a result that reproduces. Scorecard's
   Vulnerabilities check queries `api.osv.dev`, so its result changes whenever an advisory is
   published, with no change to the repository. When that host is blocked, it also scores 10.
   osv-scanner's `--offline` mode reads a local database instead. `scripts/ci-tools.sh rustsec-osv`
   builds that database from `rustsec/advisory-db`'s `osv` branch, fetched by commit id. Git
   checks the content against that id, so no separate checksum is needed. A new advisory changes
   the result only when a maintainer moves the pin, in a pull request where the new findings are
   fixed or justified. CI, pages and `scripts/regen-site-report.sh` install the same pin.
2. **Why osv-scanner.** It prints SARIF, so it needs no new parser and no fitting. It reads the
   same RustSec advisories as cargo-audit and cargo-deny, which print only their own JSON. Its
   ignores live in its own config file, so `osv-scanner scan source --offline --lockfile
   Cargo.lock` gives the same findings outside the box (take-it-out, B1).
3. **Why justify rather than upgrade, here.** At the pin, the two findings are RUSTSEC-2026-0543
   (chrono) and RUSTSEC-2026-0555 (chrono-tz). Both are informational "unmaintained" notices,
   with no vulnerability and no fixed version. Both come only through cel 0.16's default `chrono`
   feature, which CEL's timestamp and duration types need. Dropping that feature would change
   the expression language. Upstream's move to jiff (cel-rust#461) is open, and jiff's range is
   shorter than CEL's timestamp range. The reasons are in `osv-scanner.toml`.
4. **Why no expiry on an ignore.** osv-scanner's `effectiveUntil` would bring a finding back on a
   date, failing unrelated pull requests with no change to the repository. Moving the pin is the
   review point instead.
5. **Not covered.** The experiments' lockfiles are archived harnesses that are not shipped. The
   npm lockfiles would need a second pinned database (GitHub's advisories for npm), so they are
   left for later. Bumping the pin is a manual step: Dependabot doesn't track it.
