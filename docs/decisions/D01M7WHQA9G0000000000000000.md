# D79. Judgement is pushed by coding agents, not pulled by Toolbox, and every part of a portal's model is scored

**Judgement is pushed by coding agents, not pulled by Toolbox, and every part of a portal's model is scored.** Supersedes D71's proposed LLM assessment. Manifests declare `rubrics` (kind, criteria, a `subject` field that versions the assessment, default `hash`); `toolbox assess brief` and the read-only `assessment_brief` MCP tool brief the developer's own agent; it writes an assessment (`schema/assessment.schema.json`: per-criterion pass/fail/unsure with reasons) as a file in `assessments/` (read by the workspace connector's `assessments` globs) or pushes it to Postgres with `toolbox assess submit` (a remote connector's `assessment` record); `toolbox assess check` validates files and reports fresh/stale/missing. Toolbox holds no model keys and calls no model. Assessments are stale when the subject's content hash changes, and the scorecards that read them are `ratchet: {advisory: true}` (reported, outside the baseline, never gating). `toolbox describe portal` (alias `scorecards`) adds `kind`, `field` and `connector` records with content hashes; Toolbox for Toolbox scores them with `meta-kind`, `meta-field` and `meta-connector` (new ones must reach bronze), and judges its rules, scorecards and crates with `rule-quality`, `scorecard-quality` and `crate-design` through advisory `review-*` scorecards. Field usage (`readBy`) is information, not a rule; relations, map rules, tests, rubrics, authorization and actions are covered by validate, diagnostics or other reviews (holistic table in the design doc). Lazy `inbound` lists are indexable
