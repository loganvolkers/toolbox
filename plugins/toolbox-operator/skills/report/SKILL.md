# toolbox report

1. Skip connectors that need a network or a long run when the baseline was built that way.
2. Compare with --baseline. A new failure, larger evidence or a larger `measure` is a regression and the exit code is 1. A rule whose connector was skipped is `unknown` and is not a regression. An unknown whose connector ran still fails `--ci` and `--update`. A plain check passes it, so a gate that must not run without its tools (a kit's `optional: true` tool not installed) adds `--fail-on-unknown`.
3. Write the baseline with --update only after reading the diff. --ci fails when the file is stale. The ratchet verdict is the gate. The pages workflow generates the HTML and does not commit it.
4. Refresh the hosted page with `-o web --out DIR`. The page has Overview, Catalog, and Scorecards; follow the `report-ux` skill when changing that UI.

```
toolbox report portal --skip runner,github-actions --baseline portal/results.json
scripts/regen-site-report.sh
```

In a pipeline, add `--verdict verdict.json`: it lists each regression as `{scorecard, entity, message, detail, causes}`, so the job can annotate or comment without parsing the text.

With --baseline (or --against) and neither `-o` nor `--out`, the output is the verdict alone, on stdout. When a rule's evidence grew, only the new items are listed, marked `+`, and the items already in the baseline are counted ("and 9 already in the baseline"). Fix the `+` items. Add `-o md` to see every scorecard as well.

Read the root cause under each `✗ worse` line before changing anything: the evidence, the `reproduce:` command (run it to see the finding with the tool alone), and for a repository level the scorecard that fell and the change that made it fall. Fix that change; don't update the baseline to hide it.

To work the failures, `-o failures` prints each one as JSON with its path, fields, measure, evidence, fix and the connector records it came from. `-o json` adds `campaigns`, and with --baseline each one's paydown since its recorded start. The default Markdown lists only entities with a failing or unknown rule; `--all` lists every one.

To see what one change did, use `--against <commit>` (for example `HEAD~1`, or a pull request's base). It scores the portal at that commit in a temporary worktree and compares, without a baseline file.

`-o standard` prints the portal's STANDARD.md from its manifest: rules, fixes, package parameters, campaigns, commands and a CI workflow. Regenerate it rather than editing it.

For an intended change to a standard (a lower limit, a wider pattern), use `--update --accept <scorecard>`. It records and lists that scorecard's regressions and restarts its campaigns, keeping each old start under `restartedFrom`. Regressions elsewhere still fail.

**Upgrading a pinned tool** (or adding one whose files already have findings): bump `version` under `tools:` and in the CI install step (`toolbox tools config` prints installer input from the pin), run `toolbox doctor`, then `toolbox report … --baseline … --update --accept <that tool's scorecard> --keep-campaigns`. The new findings are recorded for that scorecard only, and its campaign keeps its start, so they show as the campaign going backwards. Without `--keep-campaigns` the campaign would restart at the new count.

Do not pass --update to hide a regression that has not been reviewed. If it fails, read the evidence first.
`site/public/report/` is generated by the pages workflow and is not committed; preview it with
`scripts/regen-site-report.sh` so zizmor 1.32.0 and actionlint 1.7.12 match CI (a bare `-o web`
without those tools writes `unknown` for ci-lint rules).
