# derived-state-scale

**Question** ([adversarial-critique.md](../../docs/adversarial-critique.md) §10, E4): at Seikika's v1.0
scale target ([plan.md](../../docs/plan.md) §6.6: 100k entities, 2M relations, 10k users, 1k teams,
100 rules), how long does a *full* recompute of every derived value take, with no incremental engine?
And can plain Postgres (views and materialised views) and an unmodified OpenFGA server do the same job?

**Answer (2026-11-19, 4 vCPU Xeon @ 2.1 GHz, 15 GB):** yes, with a wide margin.

| Pipeline | Full recompute | Single-entity change |
|---|---|---|
| Rust + cel-rust, 4 threads | **3.0 s** (2.9 s of it is CEL: building values and evaluating rules) | 0.35 ms (median entity), 1.5 ms (entity with 6,337 dependents) |
| Rust + cel-rust, 1 thread | 11.8 s | same |
| Postgres 16 materialised views (no permission view) | **2.6 s** | entity page computed on read from plain views: 0.4–2.3 ms per query |
| Postgres: also materialise ListObjects for all 10k users (12.6M rows) | +18.5 s | — |
| OpenFGA v1.22.1 sidecar reading the derived tuples through a Postgres **view** | — | Check p50 2.4 ms, p95 3.6 ms over HTTP; owner change visible after a 2.6 s refresh |

Both pipelines produce **identical results** (average rules passed 67.6; levels 946/22,962/56,420/19,672;
1,140 entities with all dependencies ≥ bronze; max fan-in 6,337; root roll-up 84,118; 217,117 tuples;
12,640,370 user→service permission pairs), and OpenFGA agreed with the SQL permission view on
**2,000/2,000** sampled checks and on a ListObjects result (667 = 667).

## What the pipeline computes

Each entity has two source fragments (git and a connector). Every stage is recomputed from scratch:

1. merge by per-field precedence (git > connector), as [source-of-truth.md](../../docs/design/source-of-truth.md) declares;
2. build CEL values (20-element dependency list per entity);
3. 100 CEL rules per entity (10 templates × k; same as [full-recompute](../full-recompute)) → levels;
4. cross-entity aggregates over 2M skewed `dependsOn` edges: dependents count, and "minimum level of my
   direct dependencies" (a rule that reads other entities' rule outcomes);
5. team closure (1,000 teams, 5-ary tree) and inherited-ownership roll-ups; domain roll-ups;
6. OpenFGA-style tuple derivation (owner, parent, member);
7. optionally, a materialised permission view: `user → services` they can see details of (owner team or
   any ancestor team), i.e. ListObjects for every user.

The single-entity update changes one entity's git `owner` and `tier`, then recomputes only what that
change touches (its rules, its level, its dependents' dependency check, both owners' ancestor
roll-ups, the permission-view delta) with hand-written invalidation.

The SQL pipeline ([sql/pipeline.sql](./sql/pipeline.sql), generated by [sql/gen_sql.py](./sql/gen_sql.py))
translates the same 100 rules to SQL. One simplification: the `tags.exists(t, t == 'pci')` template
reads a boolean column in SQL.

## Run

```bash
# Rust full recompute + single-entity update (entities, threads)
cargo run --release -- 100000 4
# Postgres 16: loads the same world (CSV) into a throwaway cluster and runs sql/bench.sql
CSV_DIR=/scratch/csv PGDIR=/var/lib/postgresql/dss ./run-postgres.sh 100000
# OpenFGA sidecar over a tuple view, differential check against SQL (after run-postgres.sh)
OPENFGA=/path/openfga FGA=/path/fga ./openfga/run.sh
```

Pinned: cel-rust `004a4b8`, rayon 1.12.0 (`Cargo.lock`), rustc 1.97.0, PostgreSQL 16.15 (Ubuntu
package, JIT on, `shared_buffers=2GB`, `work_mem=256MB`), OpenFGA v1.22.1 built with Go 1.26.11, fga CLI
v0.9.0.

## Caveats

- Synthetic data and rules; no I/O to sources; no search indexing or embeddings.
- The single-entity path is hand-written invalidation. It is exactly the code
  [principal-review.md](../../docs/principal-review.md) §2.2 calls a bug farm, but at these costs it is
  only needed for latency, not for throughput: a full recompute every few seconds is affordable.
- The OpenFGA `tuple` view is read-only. OpenFGA's write, `ReadChanges` and changelog paths are not
  exercised. The view was tested only with this model (no conditions, no wildcards).
