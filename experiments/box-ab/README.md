# The Box A/B: Several Tools, One Box or Hand-Written Glue

**Question:** when a repository already runs several tools, does keeping them in Toolbox's box cost
a coding agent less than the CI glue teams write by hand? The tasks are adding, upgrading, swapping,
ratcheting and reading tools, and both arms must keep each tool usable on its own.

**Status: designed, not run.** This tests the box, not tool building
([toolbox-and-tools.md](../../docs/design/toolbox-and-tools.md)). The standards A/B
([../standards-ab](../standards-ab/README.md)) compared building a tool with Toolbox's
primitives against writing a Python script, and Toolbox lost. That was the wrong half. Teams
rarely lack a linter; they lack one place that holds all of them. They need to know each tool's
pinned version, keep one baseline, know whether a pull request made anything worse, and track
the jobs left. This plan comes after the box's first internal use (§1), and its phases are built
on what that use showed.

## 1. What using the box on Toolbox for Toolbox showed

The SARIF slot, take-it-out, compact baselines, `--against`, `-o standard`, vendoring and the
local campaign were built, then used on this repository. T4T added a tool it didn't carry, ruff,
and moved zizmor onto the slot.

| What happened | Layer | Lesson for the A/B |
|---|---|---|
| Putting ruff in the box by hand took a 90-line standard (connector, kind, map, scorecard), fixtures, tests, and the version pin in four places. The [`sarif` package](../../packages/sarif/README.md) made it a 15-line `include` | Box | Adding a tool is where the box should win most. Measure it directly (phase 3) |
| The pin still lives in four places: `tools:`, `ci.yml`, `pages.yml` and the site-report script. The box knows the pins (`toolbox doctor --mise`) but doesn't install them | Box | Expect the box arm to pay this too. Score installed-and-pinned as part of correctness |
| zizmor moved from its fitting to the SARIF slot with identical results. take-it-out passed first time for zizmor, actionlint, ruff and semgrep (26 records on T4T, 33 on PostHog) | Box | take-it-out is cheap to require of both arms; make it the parity check |
| Adding a tool whose files already have findings would have dropped T4T's repository level, which reads as a regression. Cleaning up or configuring the tool first was the only way | Box | Phase 3 adds a tool whose files already have findings: the realistic case |
| The ratchet flagged the repository level falling, but its cause, a new doc at `none`, was listed only as a change, and `--against` showed the same | Box | Phase 6 asks a reader *why* a gate failed, not only whether it did |
| `portal/STANDARD.md`, generated by the box, was then scored as a hand-written doc and failed a docs rule. It had to be excluded | Box | Generated files need marking; count any such exclusion as friction |
| A stricter package check (`tighten` needs a default) broke an old vendored copy on upgrade | Box | Phase 4 upgrades a tool and a kit together |
| `--against` reruns every connector in a worktree, so a connector that runs a repository-relative binary (`target/debug/toolbox`) failed there and had to be skipped | Box | Tools must be on the `PATH`, not built in the repository, for per-commit gates |
| `-o standard` runs every connector, though it needs only the manifest | Box | Small; time it |
| semgrep's SARIF lists only files with findings, so a fixed file disappears. Compact baselines now count that as fixed | Box | Swapping a tool (phase 5) can change which files have records |
| The permission policy refused running a secrets scanner (gitleaks) over the repository | Experiment | Choose tools the sandbox allows; say so in the limits |

## 2. Setting

**The PostHog fork:**
- Its CI already runs semgrep (43 rules), mypy, actionlint, ruff, oxlint, stylelint and prettier.
- It has two pieces of its own glue: `hogli`'s workflow linter, and `check-idor-model-coverage.py`,
  a ratchet with a committed `baseline_unmigrated.txt`.

That is the realistic case: tools that already exist, and glue that grew around them.

Tools for the A/B are limited to those that run offline in the sandbox and have SARIF or JSON
output: semgrep, ruff, actionlint and zizmor. mypy and oxlint join if their versions install from
the package registries.

## 3. Arms

| | Arm A: glue | Arm B: the box |
|---|---|---|
| Given | The repository, its tools, Python and the shell | The same, plus `toolbox` and its docs, packages and starter |
| Builds | Whatever it chooses: scripts, baseline files, workflow steps | A portal: kits (`sarif`, `semgrep`, `github-actions`), a baseline, campaigns |
| Must keep | Every tool runnable on its own, with its own config | The same, checked the same way |

**One take-it-out check for both arms:** for every finding an arm reports, the documented command
for that tool reproduces it when run alone. `scripts/take-it-out.py` does this for the box. Arm A
documents its commands, and an independent script reruns them the same way.

## 4. Phases

Each phase starts a fresh agent with the repository and what earlier phases left.

| # | Task | Scored by |
|---|---|---|
| 1 | **Gather.** Put semgrep, ruff and actionlint under one gate: a pull request fails when any of them gets worse, with one baseline per tool or one for all. Report per tool and in total | Counts per tool against the tools run directly; the gate on scripted changes |
| 2 | **Campaign.** Pay down semgrep's suppressed findings (104 in 33 files) and ruff's existing findings, with progress from a recorded start | Correct starting points and paydown after scripted fixes |
| 3 | **Add a tool** whose files already have findings (zizmor on the workflows), without failing CI on them | Findings recorded, gate still green, take-it-out parity |
| 4 | **Upgrade** ruff to a newer version that reports more, on purpose, without hiding a regression from another tool | New findings accepted for ruff only; a planted semgrep regression still fails |
| 5 | **Swap** `check-idor-model-coverage.py`'s regex ratchet for a semgrep rule over the same models | Same violations; history kept or restarted, and said which |
| 6 | **Read.** Which tool failed the last pull request, on which file and line, and why; the exact command that reproduces it; each campaign's progress | Accuracy, from the artifacts alone |

**Measured:**
- tokens, tool calls and time per phase;
- the lines of glue each arm leaves to maintain (scripts and workflow steps, not the tools' own
  config);
- correctness, and take-it-out parity.

## 5. The bar, set before running

The hypothesis is about the box, not R3: **several tools in a box cost less to maintain than glue.**
- **The box passes** if, over phases 1 to 6, it uses fewer tokens and leaves less glue than arm A,
  with equal correctness, and both arms pass take-it-out.
- **It fails** if either measure is worse. Then the box's value is the format it standardises,
  not the work it saves, and the plan should say so.

Adding this hypothesis to [repo-value.md](../../docs/design/repo-value.md) is a decision to make
before the run.

## 6. Checking parity

The take-it-out check the box arm must pass, as it runs on this repository today:

```bash
toolbox connector records --portal portal --name maintainer-python   # each record's command
python3 scripts/take-it-out.py portal ci-lint maintainer-python      # rerun alone; counts must match
```

## 7. Limits

- One run per phase and arm, on one repository: indicative, not significant.
- The box arm uses tools Toolbox's own maintainers chose to slot (SARIF). A tool with only a
  bespoke format costs the box a fitting, and isn't tested here.
- Tool availability is limited by the sandbox (no secrets scanner, §1).
