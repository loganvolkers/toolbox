# Toolbox for Toolbox: standards

Generated by `toolbox report portal -o standard` from the portal's manifest; regenerate it, don't edit it. Toolbox is the box these standards are carried in; the tools that check them run on their own too (each record's `command`).

## Agent instruction files

Each agent instruction file: one canonical AGENTS.md with aliases pointing at it, links and commands that work in CI, and no hidden text or credentials (D75, D82, D83).

**Why:** Agents load these files as standing instructions for every change to the repository, and a second, divergent copy is followed by one harness and ignored by another. Bronze is one source whose links work, plus the two safety items; silver says how to test and fits in context; gold points at the decision log and names only checks CI runs.

See [AGENTS.md standards](https://github.com/loganvolkers/toolbox/blob/main/docs/design/agents-md-standards.md), [Decision: agent instruction files are scored](https://github.com/loganvolkers/toolbox/blob/main/docs/decisions/D01M7W4Y2K00000000000000000.md), [agents.md format](https://github.com/agentsmd/agents.md).

## Assessments are well-formed

What every assessment must contain to be worth reading: a named assessor, suggestions for findings and citations that resolve in the repository (D80).

**Why:** Agents act on assessments and review cards read them, so a malformed one misleads twice: a finding without a suggestion can't be acted on, and a reason without a citation can't be checked. Bronze is the ratcheted floor every new assessment must meet; silver and gold ask for citations, first on findings, then on every verdict.

See [Decision: assessments are scored](https://github.com/loganvolkers/toolbox/blob/main/docs/decisions/D01M7WJVW700000000000000000.md), [Scorecards for scorecards](https://github.com/loganvolkers/toolbox/blob/main/docs/design/scorecards-for-scorecards.md#61-assessments-and-rubrics-are-standards-too-d80), [assess-entity skill](https://github.com/loganvolkers/toolbox/blob/main/plugins/toolbox-operator/skills/assess-entity/SKILL.md).

Scorecard `meta-assessment` over `Assessment` entities, owned by group:maintainers. `toolbox report` lists what fails now. *Measured* rules check facts a tool or connector read; *judged* rules pass on an agent's assessment (`toolbox assess`).

| Rule | Level | Basis | Passes when | Why | Fix |
|---|---|---|---|---|---|
| `suggests-fixes` | bronze | measured | `entity.unsuggested.size() == 0` | A fail or unsure verdict with no suggested change leaves the reader to rediscover the fix, so the finding tends to go unacted. | Add a `suggestion:` to each listed fail or unsure verdict: the change that would make it pass. |
| `assessor-named` | bronze | measured | `has(entity.assessorName) && entity.assessorName.size() > 0` | An unnamed assessment can't be weighed or challenged, and review-assessment needs the name to tell an independent review from a self-review. | Set `assessor.name` to the agent harness or person who made the assessment. |
| `cites-for-findings` | silver | measured | `entity.uncited.filter(c, c in entity.failing \|\| c in entity.unsure).size() == 0` | A finding that cites nothing a reader can open can be neither verified nor disputed; on the first run, 6 of 9 assessments fell below silver because their reasons named a behaviour without a path or a number. | In the assessment file under portal/assessments/, cite what each listed fail or unsure reason rests on, in a form a reader can open: a repository path (`crates/x/src/lib.rs:40`), a file name only one file has, a decision or question id that exists (D71, Q10), or a full URL. A section sign or a bare number alone isn't checkable. |
| `cites-everything` | gold | measured | `entity.uncited.size() == 0` | A pass is a claim too; without a citation a reviewer can't tell a checked pass from a guess, and a wrong pass hides a problem the assessment was meant to find. | Cite a source in every listed reason, passes included, in the same forms as cites-for-findings (a path, a unique file name, an existing decision or question id, a URL), so a reviewer can check the verdict. |

## Assessments, reviewed

Each assessment reviewed against assessment-quality by another assessor, advisory; reviews of reviews are not made (D80, D01M831P5QWJQ4A2FT85N5MXJQF).

**Why:** A deterministic check sees that an assessment cites something, not that the source says what the reason claims; a second assessor's review checks that. Reviews stop at one level, so assessments made with assessment-quality are skipped, and the card is advisory because a review goes stale on every edit.

See [Decision: assessments are reviewed](https://github.com/loganvolkers/toolbox/blob/main/docs/decisions/D01M7WJVW700000000000000000.md), [Findings first decision](https://github.com/loganvolkers/toolbox/blob/main/docs/decisions/D01M831P5QWJQ4A2FT85N5MXJQF.md), [Meta standards review](https://github.com/loganvolkers/toolbox/blob/main/docs/design/meta-standards-review.md).

Scorecard `review-assessment` over `Assessment` entities, owned by group:maintainers. `toolbox report` lists what fails now. *Measured* rules check facts a tool or connector read; *judged* rules pass on an agent's assessment (`toolbox assess`).

| Rule | Level | Basis | Passes when | Why | Fix |
|---|---|---|---|---|---|
| `no-open-findings` | bronze | judged | `entity.reviewFailing.size() == 0` | Failing reviews were lost among the unreviewed lines and went unacted for days; putting the assessment at none makes an open finding head the report until it is fixed or disputed. | A current assessment-quality assessment failed the listed criteria: act on its suggestions (portal/assessments/), then re-assess. If the finding is wrong, say why in a new assessment by another assessor. |
| `assessed` | silver | judged | `entity.reviewState == 'fresh' && !entity.selfReviewed` | A review by the assessment's own assessor repeats its blind spots and is no independent check; one of the first three assessment reviews was a self-review. | Run `toolbox assess brief <assessment id> --portal portal`; a different agent or person should review it. |
| `passes-review` | gold | judged | `entity.reviewState == 'fresh' && entity.reviewFailing.size() == 0 && entity.reviewUncited.size() == 0 && entity.reviewGrounded` | Gold means an independent reviewer checked the assessment against its own sources and found it sound; a review that cites only unrelated files can't have checked it. | For a listed criterion, revise the assessment file in portal/assessments/ where the review found it unsupported or incomplete, then have it reviewed again. For an item marked "fix the review", the review file is at fault: its reasons must cite what they rest on, including this assessment's file or the sources it cites. |
| `no-doubts` | gold | judged | `entity.reviewState == 'fresh' && entity.reviewUnsure.size() == 0` | A reviewer's doubt usually means a verdict rests on taste rather than a cited source, so a second assessor reading the same sources might reach a different one. | Resolve what the reviewer was unsure of, usually by citing the source a verdict rests on. |

## Performance

Start, read and recover on a 10k-component catalog, with every read authorized (Toolbox through OpenFGA, Backstage under allow-all). ISO 25010 performance efficiency and reliability.

**Why:** Every page load, agent call and CI job reads the portal, so a slow start, slow reads or a slow recovery cost all of its users at once. The bars are absolute and set before the run; Toolbox authorizes every read while Backstage runs allow-all, which favours Backstage.

See [Performance results](https://github.com/loganvolkers/toolbox/blob/main/experiments/backstage-compare/RESULTS.md#performance-and-memory), [Factor definitions: footprint, read latency, freshness and recovery](https://github.com/loganvolkers/toolbox/blob/main/docs/design/backstage-comparison.md#2-factors).

**Why:** Memory, disk and the files an adopter keeps are paid for on every instance, preview environment and upgrade, and they decide the smallest machine and team that can run a portal. Charter goal 1 promises one image plus Postgres; a heavy footprint would break that promise.

## Security defaults

Secure by default, as installed: what an unauthenticated or forging client gets, what a client token can destroy, and what an extension can reach. ISO 25010 security.

**Why:** A portal maps every service, its owners and how to reach them, and the configuration it ships with is often the one deployed. OWASP ASVS V13 asks that the default be secure for use on the Internet, so each rule probes the product as it ships, and a setting the adopter must remember to change counts as a fail.

See [Factor definitions: secure defaults and extension isolation](https://github.com/loganvolkers/toolbox/blob/main/docs/design/backstage-comparison.md#2-factors), [Static facts](https://github.com/loganvolkers/toolbox/blob/main/experiments/backstage-compare/RESULTS.md#static-facts-and-single-run-probes).

## Supply chain

What an adopter inherits: third-party packages, their known vulnerabilities, and whether the release can be verified. OpenSSF and SLSA build provenance.

**Why:** An adopter inherits every package a portal ships, as attack surface and as upgrade work, and runs it next to the catalog and its credentials. Provenance is how they prove that what they deploy was built from the published source.

See [Static facts](https://github.com/loganvolkers/toolbox/blob/main/experiments/backstage-compare/RESULTS.md#static-facts-and-single-run-probes), [Factor definition: supply chain](https://github.com/loganvolkers/toolbox/blob/main/docs/design/backstage-comparison.md#2-factors).

| Rule | Level | Basis | Passes when | Why | Fix |
|---|---|---|---|---|---|
| `packages` | bronze | measured | `entity.thirdPartyPackages <= 1000.0` | Every third-party package is code an adopter runs, scans and updates without having chosen it, so more packages mean more advisories and more upgrade churn. ## Change safety

Changing a portal safely: validate before deploy, preview the effect, upgrade without merging, roll back without surgery. ISO 25010 maintainability; DORA change failure rate and recovery time.

**Why:** A portal's bad data and outages mostly arrive with a change: a config edit, a catalog edit or an upgrade. Checking and previewing a change before deploy lowers the change failure rate, and rolling back without database surgery shortens recovery (DORA).

See [Factor definitions: upgrade cost, analysability and recoverability](https://github.com/loganvolkers/toolbox/blob/main/docs/design/backstage-comparison.md#2-factors), [Static facts](https://github.com/loganvolkers/toolbox/blob/main/experiments/backstage-compare/RESULTS.md#static-facts-and-single-run-probes).

|---|---|---|---|---|---|

Backstage's catalog validate takes `--instance`. | Keep `toolbox validate` and `toolbox test` working with no server or database. |
| `change-preview` | bronze | measured | `entity.changePreview` | Without a preview, production is the first place a change shows that it re-owned entities, moved scores or widened access; a diff before deploy catches those in review. | Keep `toolbox plan --local --base <manifest>` diffing entities, scores and tuples. |

## Org fit

Fitting how an organisation is built: one repository with no server first, then many portals joined. Conway's law and Team Topologies.

**Why:** Systems take the shape of the organisation that builds them (Conway), and teams move fastest when they can test without an integrated environment (DORA, loosely coupled teams). A portal that needs a central server first makes every team wait for the platform team; one that cannot join portals cannot grow past one.

See [Factor definition: org fit](https://github.com/loganvolkers/toolbox/blob/main/docs/design/backstage-comparison.md#2-factors), [DORA loosely coupled teams](https://dora.dev/capabilities/loosely-coupled-teams/).

Scorecard `vs-backstage-org-fit` over `Product` entities, owned by group:maintainers. `toolbox report` lists what fails now. *Measured* rules check facts a tool or connector read; *judged* rules pass on an agent's assessment (`toolbox assess`).

| Rule | Level | Basis | Passes when | Why | Fix |
|---|---|---|---|---|---|
| `repo-scoped` | bronze | measured | `entity.repoScopedWithoutServer` | A team that can score its own repository in CI, with no server, gets value before anyone runs a portal, and the platform team has nothing to operate for it. [Repo value](https://github.com/loganvolkers/toolbox/blob/main/docs/design/repo-value.md), [Decision: the report as a GitHub Action](https://github.com/loganvolkers/toolbox/blob/main/docs/decisions/D01M7VXK0480000000000000000.md) | Keep `toolbox report` scoring a repository with no server, as actions/report does. |

## Crates, reviewed by agents

Agents' judgement of each crate against crate-design, advisory, with the same ladder as review-rule plus, at gold, a second assessor's review of that judgement; a change to src/, tests/ or Cargo.toml makes a review stale (D79, D01M831P5QWJQ4A2FT85N5MXJQF).

**Why:** Deterministic rules measure a crate's form; whether it is well designed for its place takes judgement, so agents assess it against crate-design. Open findings come first at bronze, silver needs a review of the current sources, and gold a passing, grounded review checked by a second assessor. It is advisory, because a review that goes stale on every change must not gate the ratchet.

## Cargo dependencies

Each direct Cargo dependency: a bounded requirement from a registry, locked to one version across the workspace, and shared ones inherited from the workspace (D74).

**Why:** Every direct dependency is code the binary runs, so it should come from a known source and resolve the same way on every build. Bronze bounds the requirement and the source, silver locks one version, and gold declares a shared dependency once so its users can't drift; advisories and licences need a database and a policy, so they don't gate.

See [Decision: Cargo dependencies are scored](https://github.com/loganvolkers/toolbox/blob/main/docs/decisions/D01M7W4P0S00000000000000000.md), [Dependency standards design](https://github.com/loganvolkers/toolbox/blob/main/docs/design/dependency-standards.md).

|---|---|---|---|---|---|
| `version-bounded` | bronze | measured | `!entity.wildcard && entity.requirements.size() > 0` | A requirement without a ceiling accepts any future major release, so a `cargo update` or a fresh resolve can pull in breaking changes nobody chose. | `from-a-registry` | bronze | measured | `!entity.git` | A git source is code from a repository rather than a published release, so the build can't be reproduced from the registry alone; cargo-deny's `[sources]` check flags it for the same reason. | Depend on a crates.io release. ## Rules are well-formed

Each rule's form: explained, tested, decided both ways on fixtures, with evidence, readable CEL. Gold means well-formed, not good: quality is judged by review-rule (D71, D01M831P5QWJQ4A2FT85N5MXJQF).

**Why:** Every score in the portal is only as trustworthy as the rule behind it, and an untested or unexplained rule can pass everything, or fail for the wrong reason, unnoticed. Bronze is the floor every new rule must meet (tested, explained, decided on fixtures); silver adds both outcomes, evidence and a cost bound; gold asks for tests that pin both outcomes and for evidence and a fix that lead an agent to the change.

See [Scorecards for scorecards](https://github.com/loganvolkers/toolbox/blob/main/docs/design/scorecards-for-scorecards.md), [D71 one meta level](https://github.com/loganvolkers/toolbox/blob/main/docs/decisions/D01M7W0J8YR0000000000000000.md), [Meta standards review](https://github.com/loganvolkers/toolbox/blob/main/docs/design/meta-standards-review.md).

## Scorecards are well-formed

Each scorecard's form: described, tested, no empty level, fixtures that climb the ladder to every level. Gold means well-formed, not good (D71, D01M831P5QWJQ4A2FT85N5MXJQF).

**Why:** A scorecard is the ladder readers climb, so its levels must exist and be exercised: an empty level is granted for nothing, and a level no fixture reaches has never been seen to work. Bronze, tested with no empty level, is the floor for every new scorecard; silver adds a description, a reason, a fixture ladder and tested rules; gold has a fixture at every level.

See [Scorecards for scorecards](https://github.com/loganvolkers/toolbox/blob/main/docs/design/scorecards-for-scorecards.md), [The ladders](https://github.com/loganvolkers/toolbox/blob/main/docs/design/thresholds.md#3-the-ladders), [Meta gold is not good](https://github.com/loganvolkers/toolbox/blob/main/docs/decisions/D01M831P5QWJQ4A2FT85N5MXJQF.md).

| `described` | silver | measured | `entity.described` | Agents read a scorecard's description before its rules. ## Fields are well-formed

Each field: populated in the fixtures, described and given a shape, so CEL, validation and agents know what it holds (docs/design/scorecards-for-scorecards.md §5).

## Portal connectors are well-formed

## Rules, reviewed by agents

Agents' judgement of each rule against rule-quality, advisory: an open finding is none, a current review is silver, a clean, cited one with no doubts is gold (D79, D01M831P5QWJQ4A2FT85N5MXJQF).

## Repository level

The repository's level: the lowest level among its constituent scorecards, so one weak area holds the whole repository back (D86, docs/design/repo-level.md).

**Why:** An average hides the weakest area, which is where the trouble is, so each level requires every counted scorecard to reach it, and the lowest names the one to raise next. Runner-backed cards are left out so that a skipped tool doesn't drop the repository to none.

## JSON Schemas

Each JSON Schema compiled into the binary: Draft 2020-12 with an $id, titled and described, wired into the binary, with local $refs only and no credentials (D77).

**Why:** These documents are the configuration and protocol contracts the binary enforces, and it compiles them as Draft 2020-12 without fetching remote references. Bronze is a valid, identifiable schema; silver ties it to the code; gold keeps it self-contained.

## SDLC stages

| `no-write-tokens-on-risky-triggers` | silver | measured | `entity.riskyTriggers.size() == 0 \|\| entity.jobsWithWrite.size() == 0` | These triggers run in the base repository's context on events outsiders can cause, such as a fork's pull request or a comment, so a write token there puts a privileged credential within reach of untrusted input. [zizmor dangerous-triggers](https://docs.zizmor.sh/audits/#dangerous-triggers), [Scorecard Dangerous-Workflow](https://github.com/ossf/scorecard/blob/main/docs/checks.md#dangerous-workflow), [GitHub on untrusted checkout](https://docs.github.com/en/actions/reference/security/secure-use#mitigating-the-risks-of-untrusted-code-checkout) | Don't combine pull_request_target/workflow_run/issue_comment with write permissions; split privileged steps into a separate workflow. |
| `zizmor-clean` | gold | measured | `entity.zizmor.findings.filter(f, f.rule != 'unpinned-uses').size() == 0` | Low and informational findings are weak signals one by one, but each fixed or ignored with a written reason lets a reviewer tell a known trade-off from an oversight. That is polish beyond the direct risks, so it is gold. | Resolve or explicitly ignore (with a reason) zizmor's low and informational findings. |

## CI reliability

Whether green CI means good on the default branch: failures visible and counted, including those a re-run hid, every job bounded by a timeout, and a branch that rarely fails (D70; docs/design/thresholds.md for the tiers). Speed is maintainer-ci-speed.

**Why:** CI is only worth running if red means something broke and green means nothing did; flaky, hidden or hung jobs teach people to ignore it. Bronze makes failures visible and bounded and keeps the branch out of long red streaks; silver and gold each halve the share of first-try failures a reader must check, over enough runs to tell the tiers apart.

See [Thresholds and levels](https://github.com/loganvolkers/toolbox/blob/main/docs/design/thresholds.md), [GitHub Actions standards design](https://github.com/loganvolkers/toolbox/blob/main/docs/design/github-actions-standards.md).

Scorecard `maintainer-ci-reliability` over `Workflow` entities, owned by group:maintainers. `toolbox report` lists what fails now. *Measured* rules check facts a tool or connector read; *judged* rules pass on an agent's assessment (`toolbox assess`).

| Rule | Level | Basis | Passes when | Why | Fix |
|---|---|---|---|---|---|
| `main-not-stuck-red` | bronze | measured | `entity.runs.failingStreak < 3` | A default branch that keeps failing breaks everyone who branches from it, and each new failure hides behind the last. Three in a row means the break is not being fixed. | Fix the default branch before anything else: open the failed runs in the evidence, find the failing job, and fix its cause in the code or in the workflow file under .github/workflows/. |
| `still-running` | bronze | measured | `!has(entity.runs.state) \|\| entity.runs.state == 'active'` | A disabled workflow's old run history still reads green, so it would pass every run-history rule while checking nothing. GitHub disables scheduled workflows in a public repository after 60 days without activity, and anyone can disable one by hand. A workflow whose triggers simply stop matching stays active and is not caught here. [GitHub on disabling workflows](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/disable-and-enable-workflows) | Re-enable the workflow (`gh workflow enable <file>`, or the Actions tab), or delete its file from .github/workflows/ if it is retired. |
| `fail-rate-under-20` | bronze | measured | `entity.runs.firstTryFailRate <= 20` | Every red run costs someone a look, and a re-run that turns it green hides a flaky test or step; counting first-try failures stops re-runs from lowering the rate. Bronze is the first step for a branch that fails often. | Open the failed runs in the evidence, find the failing jobs, and fix their causes in the code or the workflow file. The rate is over the last runs on the branch, so it falls as passing runs replace failed ones. Re-running a failure doesn't help: a run that passed on a later attempt counts as failed, continue-on-error, `\|\| true` and skips on the default branch are caught by failures-visible, and cancelled runs are shown here. |
| `failures-visible` | bronze | measured | `entity.hiddenFailures.size() == 0` | `continue-on-error`, `\|\| true`, `set +e` and a skip on the default branch each turn a failure into a pass, so the fail-rate rules would count it green. It is their prerequisite, so it sits at bronze. | For each listed job or step in the workflow file: remove `continue-on-error`, `\|\| true` (or `set +e`), or the `if:` that skips it on the default branch. If a step is expected to fail, give it an `id:` and check `steps.<id>.outcome` in a later step, so the failure is still asserted. |
| `every-job-has-timeout` | bronze | measured | `entity.jobsWithoutTimeout.size() == 0` | Without `timeout-minutes` a hung job holds a runner for GitHub's default of 360 minutes before it fails, spending runner time and delaying the signal everyone is waiting for. | Set `timeout-minutes` on every job; the default is 360 minutes of a hung runner. |
| `fail-rate-under-10` | silver | measured | `entity.runs.decided >= 10 && entity.runs.firstTryFailRate <= 10` | At silver, failures are rare enough that each can be classified as a flake, infrastructure or a break a pull request check missed. It needs a minimum number of runs, because with few runs one failure moves the rate across tiers. | Open the failed runs in the evidence and classify each cause: a flaky test (fix or quarantine it in its test file), infrastructure (pin or retry the step in the workflow file), or real breakage merged to the branch (add the missing check to the pull request workflow). |
| `fail-rate-under-5` | gold | measured | `entity.runs.decided >= 10 && entity.runs.firstTryFailRate <= 5` | At gold, a red run on the default branch is rare enough that every one is looked at and fixed at its cause, so red keeps its meaning. | Open each failed run in the evidence and fix its cause where it lives (the test, the workflow file, or the check the pull request lacked), so that every failure on the branch is rare enough to be looked at. |

## CI speed

Whether CI answers quickly and spends no runner time on superseded commits: a cost and feedback-time concern, separate from whether CI can be trusted (maintainer-ci-reliability; docs/design/thresholds.md).

**Why:** Slow runs and runs for superseded commits cost runner minutes and queue time, and make people wait or switch task for feedback. Speed is not a correctness or security property, so it has its own card rather than holding a reliable workflow back.

See [Thresholds and levels](https://github.com/loganvolkers/toolbox/blob/main/docs/design/thresholds.md).

Scorecard `maintainer-ci-speed` over `Workflow` entities, owned by group:maintainers. `toolbox report` lists what fails now. *Measured* rules check facts a tool or connector read; *judged* rules pass on an agent's assessment (`toolbox assess`).

| Rule | Level | Basis | Passes when | Why | Fix |
|---|---|---|---|---|---|
| `cancels-superseded-runs` | bronze | measured | `entity.cancelsSuperseded \|\| !('pull_request' in entity.triggers)` | Without a concurrency group per ref, each push to a pull request starts a new run while the old one, whose result no longer matters, keeps a runner busy. [GitHub Actions concurrency](https://docs.github.com/en/actions/concepts/workflows-and-actions/concurrency) | Add, at the top of the workflow file: concurrency: group: "${{ github.workflow }}-${{ github.ref }}" cancel-in-progress: ${{ github.event_name == 'pull_request' }} A new push to a pull request then cancels its old run, while every run on main still finishes. |
| `fast-feedback` | silver | measured | `entity.runs.p90Seconds <= 900` | Past the bound, developers switch to other work while they wait and come back late to a failure. The bound is a chosen point, not a measured one. | Keep the p90 run under 15 minutes: split slow jobs, cache builds, move long suites off the PR path. |

## Third-party actions pinned

Each third-party action across every workflow that uses it: pinned to a commit SHA everywhere (D70, docs/design/github-actions-standards.md).

**Why:** A compromised action reaches every workflow that runs it, so in an incident the question is which workflows use it and at which refs. Scoring per action answers that and shows any use still unpinned; bronze is the only level because an action is either pinned everywhere or not.

See [GitHub Actions standards design](https://github.com/loganvolkers/toolbox/blob/main/docs/design/github-actions-standards.md), [Decision: GitHub Actions standards](https://github.com/loganvolkers/toolbox/blob/main/docs/decisions/D01M7VZ2DPR0000000000000000.md).

Scorecard `maintainer-action-deps` over `ActionDependency` entities, owned by group:maintainers. `toolbox report` lists what fails now. *Measured* rules check facts a tool or connector read; *judged* rules pass on an agent's assessment (`toolbox assess`).

| Rule | Level | Basis | Passes when | Why | Fix |
|---|---|---|---|---|---|
| `pinned-everywhere` | bronze | measured | `entity.pins.all(p, p == 'sha')` | One unpinned use is enough for a moved tag to run new code with that workflow's token, so an action counts as pinned only when every workflow pins it. [zizmor unpinned-uses](https://docs.zizmor.sh/audits/#unpinned-uses) | Pin this action to a full commit SHA in every workflow that uses it. Resolve the tag with `git ls-remote https://github.com/<owner>/<repo> refs/tags/<tag>` and peel an annotated tag (`^{}`) so the SHA is the commit. |

## OpenSSF Scorecard

OpenSSF Scorecard's checks, as Scorecard scores them. The box adds only the ratchet: a check's gap to 10 is the measure, so a score that drops fails a pull request and one that rises is an improvement. A check Scorecard adds in a new release doesn't fail the gate.

**Why:** OpenSSF Scorecard is an established, openly governed standard for supply-chain security, so the portal carries its checks as OpenSSF defines them rather than writing weaker copies that would compete with it. Its one level is Scorecard's own maximum, and the ratchet stops any check from falling while the gap is paid down.

See [Scorecard checks](https://github.com/ossf/scorecard/blob/main/docs/checks.md), [OpenSSF as the template](https://github.com/loganvolkers/toolbox/blob/main/docs/design/openssf-template.md), [Carry OpenSSF Scorecard decision](https://github.com/loganvolkers/toolbox/blob/main/docs/decisions/D01M82E93XAPNE0WFXEPJZ59WG4.md).

Scorecard `maintainer-openssf` over `OpenSSFCheck` entities, owned by group:maintainers. `toolbox report` lists what fails now. *Measured* rules check facts a tool or connector read; *judged* rules pass on an agent's assessment (`toolbox assess`).

| Rule | Level | Basis | Passes when | Why | Fix |
|---|---|---|---|---|---|
| `ten` | ten | measured | `int(entity.score) == 10` | Each point below 10 is a supply-chain weakness OpenSSF documents with its risk and remediation; holding every check at its current score keeps a regression from slipping in unnoticed. | Follow the check's documentation (in the evidence). The check, its scoring and its remediation are OpenSSF's. |

## Python we maintain passes ruff

Every file ruff checks is clean. The measure is its findings, so a new finding is a regression and a fixed one an improvement; a new file must arrive clean.

**Why:** A tool's findings help only if new ones can't pile up unnoticed. The tool keeps its own rules and configuration, so its findings match a run outside the portal; the portal adds one level, clean, and a ratchet that blocks new findings while existing ones are paid down.

See [The box and the tools](https://github.com/loganvolkers/toolbox/blob/main/docs/design/toolbox-and-tools.md), [SARIF 2.1.0 specification](https://docs.oasis-open.org/sarif/sarif/v2.1.0/sarif-v2.1.0.html).

Scorecard `maintainer-python` over `PythonScript` entities, owned by group:maintainers. `toolbox report` lists what fails now. *Measured* rules check facts a tool or connector read; *judged* rules pass on an agent's assessment (`toolbox assess`).

| Rule | Level | Basis | Passes when | Why | Fix |
|---|---|---|---|---|---|
| `no-findings` | clean | measured | `(false ? entity.total : entity.active) == 0` | Each finding is a defect or a risk as the tool's authors define it, and it is cheapest to fix in the change that introduces it, while its author still has the context. | Fix ruff's findings (the record's command reruns them), or, for a deliberate style, ignore the rule for those files under `[lint.per-file-ignores]` in ruff.toml with a comment saying why. A `# noqa` comment doesn't help: the check runs with --ignore-noqa. |

## Commands

Run from the repository root.

| To | Run |
|---|---|
| List every failure, with path, fields, measure, evidence and fix (JSON) | `toolbox report portal -o failures` |
| Gate: exit 1 when anything got worse than the baseline | `toolbox report portal --baseline portal/results.json` |
| What this branch changed, against its base | `toolbox report portal --against origin/main` |
| Record improvements (commit the file) | `toolbox report portal --baseline portal/results.json --update` |
| Change a standard on purpose (new pattern, lower limit) | `toolbox report portal --baseline portal/results.json --update --accept maintainer-agent-doc` |
| Campaign progress since its start | `toolbox campaign --portal portal --baseline portal/results.json` |
| See exactly what a tool ran, to run it alone | `toolbox connector records --portal portal --name <connector>` |

`--baseline` alone fails only on regressions. `--ci` also fails when the baseline is out of date (an improvement not yet recorded), so the committed file always matches the code.

## CI

```yaml
# .github/workflows/toolbox.yml
name: toolbox
on:
  pull_request:
  push: {branches: [main]}
permissions: {contents: read}
jobs:
  report:
    runs-on: ubuntu-latest
    steps:
      # Pin both to a full commit SHA, with the tag in a comment (zizmor's unpinned-uses).
      - uses: actions/checkout@<sha> # v6
        with: {persist-credentials: false}
      # The tools the portal pins must be installed first: `toolbox tools install` or your
      # installer, from the versions under `tools:`; the action runs `toolbox doctor`.
      - uses: loganvolkers/toolbox/actions/report@<sha> # <version>
        with:
          toolbox-version: "<version>"
          portal: portal
          baseline: portal/results.json
          mode: ci    # or check: fail on regressions only
```
